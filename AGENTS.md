# VX3 Simulator: agent guide

A PS1-style browser bench toy simulating a historical "full" VX3 rig from r/VXJunkies, built as a scrolling 19-inch equipment rack. Stack: Vite, TypeScript, Three.js, Vitest, ESLint, Prettier; hosted on Fly.io.

## Roles

- **Creative lead** (design, writing, gameplay code): start from the newest prompt in `doc/resume/`.
- **Devops** (dependencies, build tooling, CI, Docker, Fly.io): owns `package.json` dependencies, `vite.config.ts`, `tsconfig.json`, `eslint.config.js`, `.prettierrc.json`, `Dockerfile`, `fly.toml`, `deploy/` and `.github/workflows/`. Other agents request changes in `doc/requests/`.

## Rules

- Stay on `main`. Do not create branches or worktrees.
- Before committing, run `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test` and `npm run build`. CI (`.github/workflows/ci.yml`) runs the same five; a green CI on `main` auto-deploys to Fly.io (`fly.yml`).
- Markdown is one paragraph per line, never hard-wrapped.
- Record significant sessions in `diary/` (template in `diary/README.md`).
- Never commit `agent-mailbox.toml` or `agent-inbox.toml`.
- `README.md` is written in-universe (a workstation record, not developer docs). Keep its voice, and keep it and `doc/plan.md` aligned with shipped behaviour.

## Commands

- `npm run dev`: Vite dev server on `http://127.0.0.1:5173/` (strict port).
- `npx vitest run src/game/rig.test.ts`: run one test file; add `-t "<name>"` for one test. `npm run test:watch` for watch mode.
- `npm run format`: apply Prettier.
- `npm run build` already runs the typecheck before `vite build`.

## Architecture

- `src/main.ts` calls `startScene(canvas)` in `src/rendering/start-scene.ts`, which is the hub: it builds the Three.js scene, camera modes (orbit/isometric, first-person walking with touch sticks), input, the operator log UI and the per-frame loop that steps the rig and feeds audio and tell-tales. Most integration work lands here.
- `src/game/` is pure logic with no DOM or Three.js, and is where the unit tests live (`*.test.ts` beside the source). `rig.ts` is the live simulation (`createRig`/`stepRig`, emitting `RigEvent`s; `YALGETH_LIMIT = 0.88`). `rack-controls.ts` holds the toggle and knob ids, `rack-catalogue.ts` the modules and makers placed in the rack, `safety-telltales.ts` the wall load/kWh meter and dilation crystal, `walk-collision.ts` first-person collision, and `consequences.ts` the deadpan incident log lines.
- `src/game/rig-model.ts` (a data-driven component and influence model loaded from `doc/lore/component-catalogue.json`) and `src/game/panel-grid.ts` (a 12-column panel layout with fixed control footprints and `validatePanel`) are tested but not yet wired into the scene; they underpin the "deeper, staged power model" in `doc/plan.md`.
- `src/scene/` has one `create*` factory per lab fitting or room (lab room, corridor, ceiling services, teleprinter, Cub monitor and so on), each returning objects that `start-scene.ts` places.
- Everything fitted to a machine is designated an **input** (worked by the operator; clickable) or an **indicator** (driven by machine state; never clickable) via `src/game/machine-parts.ts`. In `start-scene.ts`, use `input()` and `indicator()` for machine parts and `fixture()` for clickable room fittings (doors, drawers, taps); never call `bind()` directly. Development builds audit the scene on load and log any violation; `vx3Walker.parts()` lists every machine's inputs and indicators. When you change what an input drives, update `doc/design/control-graph.md` (GitHub renders its Mermaid diagrams) so it stays the record of every link.
- The operator's log is for debugging the machine: every input writes a line headed `machine: control` (its designation), with what it did on the same line, and room fixtures (lights, doors, taps, drawers, the chair) write nothing. Every control needs a unique name tied to its role in the model; the column names its unwired controls `spare …, <panel>`. In development, `vx3Walker.press('machine: control')` works a control by that name and `vx3Walker.log()` reads the log.
- **No fabricated readings.** Every gauge, meter, display, readout, lamp and LED shows something from the model (`src/game/world/world.ts`): a vertex read through the world, never a value made up from time, randomness or a constant. Label each with what it actually shows. Motion that is not a reading (a fluttering ribbon, a swaying lamp, a bobbing float that follows a real flow) is fine. Something with no model behind it either gets a quantity added to the model or loses its readout. Repeating a quantity is fine: a cabinet display may show what a lamp or window on the east board shows. The column's cabinets read the world through the rig's `read` option; the developer room's unhooked copy reads a cold world of its own.
- Every knob and rotary selector turns the same way: a click on its left half turns it anticlockwise (down), its right half clockwise (up), one detent per click, stopping at its end stops (`knobDirection`, `stepKnob` and `stepSelector` in `src/scene/rotary-knob.ts`). The emergency telephone's rotary dial is the one exception: it dials numbers, not values.
- The first-generation VX3 (main rack, side cabinet, ferrocore drum, socket and mains lead) is `createGen1Vx3` in `src/scene/gen1-vx3.ts`. The lab no longer builds it. It now stands in the expanded VX-Museum, with field generators visibly removed and interactive controls driving its own isolated `src/game/museum-exhibit.ts` model (never the lab world). `src/scene/museum-vx3-exhibit.ts` supplies its pedestal: 30 s startup, 60 s demonstration, 8 s rundown; START is accepted only when inactive. Dev3 retains its cordon and a relocation notice. Keep the module: the owner does not want old work destroyed. Its rack height, `GEN1_TOTAL_HEIGHT`, is still the lab's floor datum, and `GEN1_RACK_Z` marks the bay.
- The second-generation VX3, the ferrocore column (`src/scene/ferrocore-column-rig.ts`), stands in that bay. Its vessel is `src/game/column-prep.ts`; its ferrocore drive is the drive model `src/game/rig.ts` with the rack controls (`settings`), worked from the column's panels (through the rig's `drive` hook-up) and the east board, and the drive heats the core (`driveTemperature` in `src/game/cold-start.ts`). The drive runs only with the vessel's atmosphere permit (`atmospherePermit` in `src/game/gen2-wiring.ts`: sealed, purged, at working pressure, recirculator on), and xenon reaches the machine only through the recirculator (`lineFlow`). Every warning in the installation is one of the east board's eighteen alarm windows (`annunciators` and `warningConditions` in `src/game/control-board.ts`); add new warnings there. The developer room, dev0 (`/?room=dev0`; `?room=dev` still works), shows a copy of the column driven not by the lab's wiring but by the world graph described below, worked from its KALTSTART desk (`src/rendering/dev-cold-start-board.ts`), whose two rows are the cold start in order. Dev2 (`/?room=dev2`, `src/rendering/parts-room.ts`) holds the CONTROL TEST board of panel parts; `?room=dev2&view=controls` starts in front of it.
- `src/game/world/` is the lab's machine rebuilt as a directed graph of cached functions on `@preact/signals-core` (`graph.ts`, `world.ts`): every link is declared, so `analyse()` lists dead controls, unset parameters and values the room never shows. It is not yet wired into the lab. Its failures are designed, not searched for: each has a stated cause and scripted steps in `scenarios.ts`, and a test fails if an alarm window or bad end has no scenario. When you add a warning or failure, add its scenario.
- Panel parts are components (`src/game/world/components.ts`), separate from the world model: the world says what is true (the plant is powered); a component has inputs (Power, Latch), one source of truth for its state (a bound world value, or its own), guarded operator actions, silent sets from the model, and its own sounds, transition sounds (`press`, `on`, `off`, `detent`, `end-stop`, `refused`) and state sounds held while its state calls for them (`src/audio/part-loops.ts`). The scene's part factories (`panel-switchgear.ts`, `eighties-controls.ts`) are only views; rooms play a component's sounds where the part is (`src/rendering/part-sound-hub.ts`). Sounds are emitted by objects, never by the world model. The dev0 desk and the dev2 parts board use components; the lab's panels are still to be ported.
- Inspection views are opened with `?view=…` (for example `?view=rack`, `?view=plant-room`). Only views of dev-only spaces, such as the developer room (`?room=dev0`), take a `dev_` prefix; views of the real game never do.
- Walking, looking and zoom are shared by `src/rendering/first-person.ts` (the developer room uses it; the lab's walker in `start-scene.ts` mirrors its numbers). The wheel zooms the field of view.
- `src/rendering/ps1-material.ts`: meshes use `createPs1Material` (vertex snapping via the shared `ps1Uniforms`; `unlit` for printed surfaces that dim with `roomLight`, `glow` for self-lit screens and tubes).
- `src/audio/`: `sound-parameters.ts` maps rig state and controls to plain numbers (tested); `sound-engine.ts` drives Web Audio and ZzFX from them. Apparatus audio combines procedural model-driven sounds and owner-requested edited recordings in `src/audio/assets/`. Record every sound-effect credit in `CREDITS.md`, including the author/profile, original source URL, stated licence and edits; keep the asset README for technical notes.
- The effects room (`/?room=dev1`, `src/rendering/effects-room.ts`) is where end-state effects are tuned. Its RECORD button prints the settings on the teletype and saves them as `vx3-effects-<time>-<nn>.json` to the browser's downloads folder (normally `~/Downloads`); `readEffectRecording` in `src/game/effect-settings.ts` loads one back exactly, and `vx3Dev1.restore()` puts it back in the room. When the owner mentions a recording, read it from there.
- Lore lives in `doc/lore/`: `summary.md` separates borrowed community terms from invented local parts, and modules in the catalogue are marked `provenance: 'invented'`. Keep that distinction when adding apparatus.
